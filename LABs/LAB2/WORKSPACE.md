# LAB2 工作区管理与人机协作规范

本文件是 LAB2 文件存放与协作流程的唯一维护入口。仅适用于本目录及其子目录，不约束课程仓库其他实验。自任务 T0002 落地起生效，不追溯伪造既往提交、验收或实验完成记录。

下列路径均相对于 LAB2。新增文件先确定归属；新增类别时同步维护本节。不为尚未产生的内容提前创建空目录。

### 数据、输出与命名

- 原始数据和模型初值沿用当前管理方式，不重整数据目录、不引入 Git LFS；不要用全局的 npy/npz/pdf 忽略规则误伤课程文件。
- 重跑时使用新的空输出目录，例如 outputs_T0003_20261112_01；第一题可在该运行目录下区分 expression 与 gradient。相应 --output 路径以实际运行命令为准。
- 完整输出、模型权重和日志本地保留至验收结束，不把整套结果搬进 docs/。精选图需注明来源运行与指标口径。
- Git 中的任务说明应记录未入库产物的相对路径、必要配置和运行命令；关键正式产物记录 SHA-256，以便核对本地文件。
- 忽略规则不删除或自动取消跟踪既有文件。logs/EXPERIMENT_PLAN.md 已被跟踪，按现状保留；不擅自搬迁、删改或顺便提交其中的其他改动。
- submit/ 只用于整理最终交付，不是源码或报告的唯一保存位置。

## 2. 角色、任务与记录分工

实验待补全代码由本人实现。除非用户明确改变要求，AI 只负责解释、检查、验证、方案与报告结构建议，不代填 TODO。不得把公开测试或玩具数据验证写成正式实验已完成。

一项任务必须能够独立说明目标、交付产物并接受验收，不按消息条数拆分。纯问答不建任务、不要求 commit；正式检查即使不改业务代码，也要交付检查说明并提交。

| 记录 | 职责 |
|---|---|
| docs/tasks/Txxxx.md | 可随成果传播的详细任务说明和人工验收记录 |
| _tasklog/ledger.jsonl | 本机活动事件、任务状态、交付 commit SHA，只追加 |
| _tasklog/BOARD.md | 从事件生成的本地看板，不手改 |
| _progress.md | 本地步骤与接续断点，不覆盖其他 Agent 的条目 |
| Git commit | 本任务成果与说明的版本快照，不等同人工验收 |

台账未随 Git 分发；新机器接续时先检查已有任务文档和 Git 历史，初始化或恢复本地台账，避免重复分配已有 Txxxx。缺少本地工具时先说明情况，不虚构任务状态。

## 3. 开工、交付与人工验收

1. 先读本文件、本地看板和断点，检查 Git 暂存区及工作树。若其他 Agent 已占用同一项目，先协调；待验收任务不占用执行认领，但后续任务不能擅改其验收基线。
2. 认领 in_progress，获得任务号；明确目标、范围、验收标准和执行 Agent。用 note 补充会话标识，不混淆实现者、检查者与验收者。
3. 实施并更新自己的断点条目，记录实际验证范围，编写 docs/tasks/Txxxx.md；有障碍则 blocked 并写清 blocker，取消则 abandoned 并说明理由。
4. 自检后审查 diff，只暂存本任务文件，创建交付 commit：类型(lab2): [Txxxx] 工作摘要。类型使用 feat、fix、docs、test、chore 等符合工作实质的名称。
5. 提交成功后把完整 SHA 写入本地台账，状态设为 awaiting_review。交付时提供 commit、任务说明、验证结果和人工验收步骤。提交失败不得声称已交付，应记录阻塞。
6. 人明确通过后才记 done；原任务说明追加日期、用户反馈和结论，并增加同任务号的验收文档 commit。此操作属于原任务收尾，不递归新建说明任务。
7. 未通过则在原说明记录反馈、恢复 in_progress，修复并新增 commit 后再次 awaiting_review。不得重写旧交付以掩盖返工。

### 人工验收边界

- AI 自检、请求执行或同意规划均不等于验收通过。必须有针对该次交付的明确用户反馈；记录其原意与时间，不替用户决定。
- 台账通过 human 署名及 review-note 记录人工验收。AI 仅在已有明确反馈时协助登记，不得伪造身份。
- 初次任务说明的验收栏写“待验收”。commit SHA 保存在本地台账，文档不要求包含自身 commit SHA，避免自引用循环。
- 接受交付后的文档 commit 只补验收记录；若引入实质变更，需重新交付并验收。
- 本地工具校验的是记录结构，不提供身份认证，也不能证明人真的验收过；真实用户反馈仍是必要依据。

### 提交安全

- 每项交付任务至少一个 commit。保持当前合适的 checkout，不自动建分支、push、amend 或改写历史。
- 不执行全仓库 git add .；使用明确的 LAB2 文件清单，不夹带其他实验或他人的改动。
- 存在无关暂存文件，或同文件改动无法安全分离时，先停下协调。不得通过还原他人改动来制造干净工作树。
- 发现密钥或隐私信息不写入说明和 commit，先报告并处理。

## 4. 任务说明模板

每份 docs/tasks/Txxxx.md 按以下内容组织，可根据任务增加细节，不得省略验证边界和验收部分。

1. 任务信息：编号、标题、日期、执行 Agent/会话、状态。
2. 目标与范围：成功条件、涉及内容、明确不做什么。
3. 实施说明：做了什么、原因、涉及文件及各自职责。
4. 验证记录：命令、环境、实际结果；未验证内容与已知风险。
5. 产物与复现：文件位置、必要配置、运行来源和关键产物哈希。
6. 人工验收清单：人能逐项复核的具体步骤。
7. 验收与返工记录：日期、用户明确反馈、通过或返工结论；未收到反馈时写待验收。

## 5. 本地台账接口与验收标准

具体命令见本地 _tasklog/README.md。状态流程为 in_progress → awaiting_review → done；返工回到 in_progress。等待人工验收时不得提前记 done，也不必伪装为 blocked。

新增交付事件需有真实产物、对应任务说明和完整 commit SHA；done 需来自待验收状态且具备 human 署名和明确验收记录。旧事件不回写，保留当时语义。

规范维护任务也遵守本流程。验收时检查：文件归属清楚、入库与本地边界正确、待验收与完成分开、Git 提交只含本任务内容，以及任务说明足以独立判断交付是否合格。
